# 09-08 Plan: Postgres Vector Backfill Readiness

## Goal

Close another source-owned part of Phase 09 Task 6 by making the remaining
Postgres NULL-vector backlog actionable for operators without executing a
backfill or exposing raw tenant memory content in reports.

## Scope

- Add a read-only `PostgresEngine.vector_backfill_plan()` probe.
- Reuse `vector_hygiene_snapshot()` for evidence/assertion backlog counts.
- Sample tenant/branch-scoped embeddable NULL-vector candidates from evidence
  and assertions.
- Redact raw evidence content and assertion statement text from the plan.
- Report stable row ids, SHA-256 content/statement hashes, partition, trust,
  sensitivity, backlog, sample count, and truncation status.
- Include the backfill plan in `build_ops_report()` and the static dashboard
  when the engine supports it.
- Add focused tests for redaction, SQL scoping, report inclusion, and dashboard
  rendering.

## Out Of Scope

- No automatic embedding generation or row mutation.
- No assertion embedding writer/backfill command.
- No production backfill execution evidence claim.
- No live Postgres tuning application.
- No halfvec or pgvectorscale schema rollout.
- No provider default flip.

## Acceptance

- Operators can see whether the Postgres vector backlog is empty, sampled, and
  truncated from `ops-report`.
- Candidate samples omit raw content and statement text while preserving stable
  hashes for external evidence correlation.
- Dashboard output exposes backfill backlog, sample count, and truncation state.
- The probe is read-only, tenant/branch scoped, and covered by focused tests.
