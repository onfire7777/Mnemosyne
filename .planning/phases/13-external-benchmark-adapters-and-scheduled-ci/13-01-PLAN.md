# Phase 13 Plan 01: Scheduled Deterministic Public Regression CI

## Objective

<objective>
Close the source portion of BENCH-007 with one bounded CI lane that replays only
the repository's deterministic development and adapter-contract tests on a
weekly cadence and through an identical manual trigger. This plan does not run
MemoryAgentBench or BEAM upstream protocols, does not consume official or
held-out assets, and does not change the status of BENCH-006, Phase 12 measured
closure, any benchmark claim, or any publication gate.
</objective>

## Admission and Scope Contract

### Prerequisites

- Start implementation in a fresh Worktrunk checkout whose base is a clean
  canonical `main == origin/main`; do not implement in the canonical checkout.
- Confirm no active writer owns either future implementation path and acquire
  the CI integration lease before editing.
- Treat merged PRs #74-#78 as source reality: the MemoryAgentBench scoring and
  submission-envelope contracts and the BEAM disclosure/reader-judge contracts
  exist. Do not reimplement or reinterpret those adapters in this plan.
- Phase 12 measured closure is **not** a prerequisite for this development-only
  regression lane. It remains a hard prerequisite for official/upstream Phase
  13 execution and evidence.

### Exact Future Implementation Lease

The implementation owner may write only:

1. `.github/workflows/public-regression.yml` — new scheduled/manual workflow.
2. `tests/test_public_regression_workflow.py` — new workflow contract test.

Do not edit `.github/workflows/ci.yml`, adapter code, fixtures, registry,
runner/scoring/bundle code, dependency or lock files, `GOAL.md`, `.planning/**`,
result-v2/publication surfaces, or protected worktrees. If implementation
requires any additional file, stop and return for a new lease; do not widen the
scope opportunistically.

### Deterministic Fixture and Command Scope

The workflow command is a literal allowlist:

```text
uv run --locked python -m pytest \
  tests/test_public_longmemeval.py \
  tests/test_public_hipporag.py \
  tests/test_public_memoryagentbench.py \
  tests/test_public_beam.py \
  -q
```

This scope is limited to committed, synthetic/in-memory development fixtures
and source-contract pins already reviewed in those tests. It must not discover
tests dynamically, download benchmark data, read protected/frozen/held-out
assets, invoke a real model/judge/provider, submit upstream, write public
receipts, or emit a leaderboard result. Adding a suite requires a reviewed plan
revision and proof that its fixtures, rights, network behavior, and claim state
fit this contract.

### Cadence, Capacity, and Reporting

- Use one UTC weekly cron at a fixed minute plus `workflow_dispatch`; both
  triggers run the identical job and fixed command. Do not add dispatch inputs.
  Gate manual runs to `github.ref == 'refs/heads/main'`; a dispatch against any
  other ref must skip the job.
- Use one `ubuntu-latest` worker, `permissions: contents: read`, a workflow/job
  timeout no greater than 20 minutes, and concurrency that prevents overlapping
  scheduled/manual instances. No matrix, service container, cache, artifact
  upload, paid runner, secret, token elevation, provider credential, or
  third-party reporting action is admitted.
- Pin every action to an immutable full commit SHA and pin Python, pip, and
  `uv` consistently with the canonical CI. Install only the locked development
  environment; do not add a dependency.
- Let a test or setup failure fail the job. Add at most a minimal
  `GITHUB_STEP_SUMMARY` containing event, commit SHA, fixed suite names, and
  pass/fail status. Never include fixture rows, prompts, model output,
  credentials, private paths, or case-level benchmark data.
- A red scheduled run opens an engineering regression investigation against
  source/dev behavior. It does not authorize examining protected cases,
  changing expected answers or thresholds to make the run green, selecting
  patches from held-out/test failures, rerunning an official attempt, or
  upgrading any requirement or claim.

## Threat Model

<threat_model>
  <boundary>GitHub event metadata and repository contents cross into a hosted runner with a read-only repository token.</boundary>
  <threat severity="HIGH">Dispatch or matrix input reaches shell execution and permits arbitrary commands, suite selection, provider selection, or asset selection.</threat>
  <mitigation>Define no workflow-dispatch inputs or matrix, require manual dispatch to target `refs/heads/main`, and execute one literal argv-like shell command over four fixed test paths. The contract test rejects non-default-ref dispatch, interpolation, dynamic discovery, mutable action references, and privileged permissions.</mitigation>
  <threat severity="HIGH">The scheduled lane accidentally consumes held-out/private assets or invokes paid/network providers, turning regression CI into a measured or tuning surface.</threat>
  <mitigation>Allowlist only source/dev contract tests, provide no provider secrets, reject download/provider/submission commands, and fail the contract test if official, held-out, frozen, private, receipt, publication, or leaderboard paths appear.</mitigation>
  <threat severity="MEDIUM">Unbounded concurrency or runtime creates avoidable CI cost or overlaps an authoritative measured run.</threat>
  <mitigation>One worker, no matrix/services, maximum 20-minute timeout, one non-overlapping concurrency group, and no operator/measured evidence paths. Evidence/operator admission remains external and serialized.</mitigation>
  <threat severity="MEDIUM">Workflow output leaks sensitive benchmark data or is mistaken for publishable evidence.</threat>
  <mitigation>No artifacts or external reporting; summary metadata is limited to event, SHA, fixed suite labels, and status. The lane emits no benchmark bundle, receipt, score, or claim state.</mitigation>
  <residual_risk>The hosted runner and third-party actions remain supply-chain boundaries; full-SHA action pins, read-only permissions, locked dependencies, and exact-head review reduce but do not eliminate that risk.</residual_risk>
</threat_model>
