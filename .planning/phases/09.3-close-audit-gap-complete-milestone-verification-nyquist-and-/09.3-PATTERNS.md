# Phase 09.3 Evidence Patterns

## Pattern 1: Reconstructed Artifact Header

Every retroactive artifact states:

- `reconstructed: true`;
- the reconstruction/verification timestamp;
- the current SHA under test;
- current, retained repository, and retained external evidence separately;
- claims that remain deferred or out of scope.

This makes the repair auditable without pretending the artifact existed during
the original phase execution.

## Pattern 2: Requirement Truth Table

Use one row per requirement with these columns:

| Requirement | Observable truth | Primary evidence | Supporting evidence | Disposition |
|---|---|---|---|---|

`Disposition` is `VERIFIED`, `DEFERRED (non-blocking)`, or `BLOCKED`. Never use
ambiguous prose such as “implemented” as a verification result.

## Pattern 3: Nyquist Coverage Matrix

Validation files map each critical seam to a focused check and a backstop:

| Seam | Focused check | Backstop | Cadence | Failure action |
|---|---|---|---|---|

Every major phase goal must have at least one direct focused check. The full
suite alone is not sufficient sampling evidence.

## Pattern 4: Current vs Retained Evidence

- **Current:** rerun at the Phase 09.3 closure SHA.
- **Retained repo:** commit, summary, CI record, or gate artifact already in git.
- **Retained external:** custody-verified operator bundle outside git.
- **Historical statement:** dated narrative, never treated as a current pass by itself.

## Pattern 5: Canonical Requirement Ownership

Each REQ/NFR has one primary implementation phase in `REQUIREMENTS.md`. Later
hardening/production phases are supporting closures. Verification documents may
name a requirement when they directly exercise it, but summaries add
`requirements_completed` only for work that actually completed that ID.

Archived Phases 0-5 need one retrospective summary each because strict GSD
requirements coverage joins requirement ownership, verification, and summary
frontmatter. Those summaries cite the retained plan and verification and are
labelled reconstructed; they do not claim contemporaneous execution metadata.

## Pattern 6: Supersede, Do Not Erase

When old text says “pending” and a later verified operator capture closed the
item, retain the historical statement and add a dated supersession note with the
new evidence. Do not silently rewrite the past tense into a claim that was true
at the earlier date.

## Pattern 7: Honest Deferred Boundaries

An operational adoption or live-performance item may remain deferred while the
phase passes if it was explicitly outside the source-owned completion contract.
The aggregate verification must name it, explain why it is non-blocking, and
point to the future evidence action. Deferred is never rendered as verified.
