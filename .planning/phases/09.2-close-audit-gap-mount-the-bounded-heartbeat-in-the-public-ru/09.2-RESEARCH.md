# Phase 09.2 Research: Public Runtime Heartbeat Mount

## Research conclusion

Mount one in-memory `ShadowWorkspaceService` beside the existing queue worker in
`cmd_worker_run`, start it once per bounded command invocation, and tick it once
after every existing worker cycle. This is the smallest integration that makes
the Phase 7 heartbeat real in the supported public/deployed lifecycle without a
new scheduler, daemon, process, persistence model, or authority path.

The source-owned proof should be an additive, compact structured heartbeat
projection in each worker cycle, a final top-level heartbeat summary, and
low-cardinality entries in the existing `MetricsRegistry`. The service window
must **not** be persisted in `RuntimeState`, SQLite, or Postgres. The production
supervisor already treats each `worker-run` process as a bounded window; a fresh
process is the correct reset boundary after a normal exit or unhealthy
heartbeat exit. Retained deployment-soak stdout plus release-audit validation
is the durable evidence surface.

## Existing runtime flow

1. `infra/entrypoint.sh` runs the `consolidator` role as a supervisor loop.
2. Each loop invokes `mneme --backend postgres --queue-backend postgres
   worker-run --poll-interval ...` and sleeps before restarting it.
3. `cmd_worker_run` validates cadence arguments, then calls
   `_runtime_worker_components` once.
4. `_runtime_worker_components` constructs the tenant-scoped runtime state,
   queue, `MemoryTools`, one `MetricsRegistry`, `RuntimeJobHandlers`, and
   `QueueWorker`.
5. Each bounded worker cycle calls `QueueWorker.run_once` up to `--limit`,
   persists existing queue/learning/user-model state, snapshots the queue, and
   preserves idle-exit/polling semantics.
6. `cmd_worker_run` emits one final JSON document and exits nonzero only for its
   current fail-closed conditions.
7. Production soak invokes the same command against the isolated
   `release-worker-probe` Postgres tenant. `release-audit` validates its retained
   structured stdout through `_release_worker_run_evidence_findings`.

The public host is therefore already backend-neutral above queue/runtime
adapters and already supervised in production. Request-scoped MCP/API
construction is stateless and has no correct lifecycle ownership for this
service.

## Existing heartbeat contract

`ShadowWorkspaceService` already owns all cognitive-window state:

- explicit `start()` resets and opens one bounded window;
- `tick()` enforces controller item limits, max cycles, anti-rumination,
  proto-self regulation, one-dreamer-per-window, and terminal hard stops;
- a terminal hard stop sets `running=false`, and the next tick raises without
  mutating the accumulated cycles or trace;
- `stop()` closes the lifecycle without resetting the window;
- `ShadowWorkspaceServiceReport` exposes the existing
  `always-on-heartbeat-safety.v1` report, tick/max-cycle bounds, stopped reason,
  metacognition, and the `shadow_only=true`, `critical_path=false`,
  `production_mutation=false`, `promotion_gate_required=true` authority
  contract;
- selected content and trace content are hashed/redacted by the existing report
  serializers, while item metadata is preserved and therefore must be strictly
  allowlisted by the runtime adapter.

The existing `heartbeat_safety` payload is the canonical safety source of
truth. Do not fork its calculations in CLI code.

## Recommended integration shape

### Component and lifecycle ownership

Construct the service in `cmd_worker_run`, immediately after
`_runtime_worker_components`, and call `start()` before entering the existing
cycle loop. The command owns exactly one service instance and one last-good
service report for its whole invocation.

After queue work and `_persist_worker_state` complete for a cycle, call the
service exactly once:

- productive cycle: pass allowlisted `WorkspaceItem` rows derived from the
  completed/retried/dead jobs in that cycle;
- idle cycle: pass an empty item list so the existing service creates its
  bounded idle/default-mode item;
- never call the service from inside the per-job loop;
- never use its result to select jobs, change queue state, retry, promote,
  retrieve, rank, write memory, or adjust polling.

Use `finally` only to close lifecycle state and finish report construction; do
not call `start()` again after a hard stop. Once unhealthy, freeze the service
for the rest of the invocation, continue safe queue bookkeeping/cycles, emit a
compact unhealthy heartbeat result for each remaining cycle, then exit nonzero
after emitting the final report.

### Job-metadata adapter

Add one private, deterministic adapter in `src/mnemosyne/cli.py` rather than a
new module or dependency. It should create at most the service's existing
`max_items_per_tick` bound and include only:

- item `id`: job id (already present in the public worker report);
- fixed priority and fixed non-sensitive content such as `worker job metadata`;
- source: a fixed value such as `worker_cycle`;
- metadata: `tenant_id`, `job_id`, `kind`, final `status`, `cycle`, and a small
  allowlisted `outcome_class` (`complete`, `retry`, `dead`, or `other`).

Never copy `payload`, `result`, `last_error`, exception text, evidence content,
prompts, provider output, access tokens, connection data, or arbitrary job
metadata. The adapter must use `runtime_state_tenant(args)` as the sole tenant
source; no global/system fallback is permitted when `--queue-tenant`/`--tenant`
is present. The existing workspace validation then rejects mismatched tenant
metadata.

### Public report schema

Do not attach the full cumulative `ShadowWorkspaceServiceReport` to every
cycle. That would repeat a growing stream and produce avoidable quadratic
output. Add a small versioned projection, for example
`worker-workspace-heartbeat.v1`, derived from the latest canonical service
report:

- `schema_version`;
- `ok` and lifecycle state (`running`, `stopped`, or `unhealthy`);
- `tick_count` and the worker `cycle` represented;
- `stopped_reason`;
- the canonical `heartbeat_safety` object, including its
  `always-on-heartbeat-safety.v1` version and compute bounds;
- `shadow_only`, `critical_path`, `production_mutation`, and
  `promotion_gate_required`;
- a fixed, sanitized failure code when applicable (never exception text).

Every `cycles[]` row should receive this compact cumulative projection. A
top-level `workspace_heartbeat` should contain the final projection after the
service is stopped, plus a count proving one tick was attempted per worker
cycle until a terminal/failure freeze. Existing worker keys remain unchanged.

The top-level worker `ok` value should be the conjunction of the existing dead
job condition and heartbeat health. A terminal safety hard stop is an explicit
unhealthy result even though it is expected safety behavior. A caught heartbeat
exception becomes a fixed redacted failure (`workspace_heartbeat_failure`),
leaves already-safe queue effects intact, and forces exit 1 after JSON emission.

### Metrics

Use the existing per-invocation `MetricsRegistry`; do not introduce a metrics
backend or labels. Recommended low-cardinality names are:

- counters: `workspace.heartbeat.ticks`,
  `workspace.heartbeat.productive_ticks`,
  `workspace.heartbeat.idle_ticks`, `workspace.heartbeat.hard_stops`, and
  `workspace.heartbeat.unhealthy`;
- samples/gauges: `workspace.heartbeat.duration_ms` and
  `workspace.heartbeat.estimated_compute_ms`.

Count a tick attempt once, classify productive/idle from the worker cycle, and
count hard-stop/unhealthy transitions once rather than once per later frozen
cycle. Never use tenant, job id, kind, exception class, or stopped reason in a
metric name/label.

## Failure semantics

Heartbeat failure is fail-visible but non-authoritative:

1. Queue work and its existing persistence complete first.
2. The heartbeat receives metadata only after the job outcome is known.
3. A service exception or invalid report is caught at the heartbeat boundary,
   converted to a fixed redacted failure code, and freezes further ticks.
4. Remaining bounded worker cycles may safely continue under their unchanged
   scheduler so jobs are not stranded by an advisory path.
5. The final worker report has `ok=false`, contains the failure/hard-stop proof,
   is emitted exactly once, and the command exits 1.
6. `infra/entrypoint.sh` logs its existing generic nonzero message and restarts
   a fresh bounded process window. It must not print the internal failure body.

Do not swallow `KeyboardInterrupt`/`SystemExit`, weaken queue failure handling,
or place the heartbeat around the queue handler itself. Catch ordinary
`Exception` only at the shadow boundary, matching the queue worker's bounded
failure style while emitting less detail.

## Persistence decision

No new runtime-state persistence is needed or desirable.

- `start()` intentionally resets a bounded service window.
- The supervisor/process invocation is the accepted lifecycle boundary.
- Persisting trace, proto-self, selected metadata, or safety counters would
  create a new privacy, schema, migration, and cross-process consistency
  surface that no requirement needs.
- Resetting persisted counters could accidentally defeat or distort the
  existing hard-stop semantics; carrying them across processes could make a
  healthy supervised restart permanently unhealthy.
- Source-owned public proof already exists through worker JSON, metrics in that
  JSON, retained deployment-soak output, and release-audit.

If future operator requirements need longitudinal telemetry, export the
low-cardinality metrics through the existing operations pipeline. Do not make
the cognitive workspace itself durable in this phase.

## Release and production evidence implications

Update `RELEASE_AUDIT_REQUIRED_OUTPUT_KEYS["worker-run"]` additively to require
the top-level heartbeat section. Extend
`_release_worker_run_evidence_findings` to reject evidence when:

- the top-level or per-cycle heartbeat is missing/malformed;
- `tick_count` does not advance with cycles or the final count is stale within
  the same invocation;
- the canonical safety schema version is wrong;
- compute is unreported/unbounded or tick/max-cycle values are invalid;
- `shadow_only` is not true, `critical_path`/`production_mutation` are not
  false, or `promotion_gate_required` is not true;
- a heartbeat claims healthy while hard-stopped/unhealthy;
- the final report and final cycle disagree;
- a failure/hard stop is paired with top-level `ok=true`.

This validator should share one small shape-check helper with worker evidence
logic rather than duplicate heartbeat semantics in test fixtures. Update the
canonical production soak worker fixture and manifest/renderer expectations.
Keep `worker-ops-check`'s external **supervisor freshness heartbeat** distinct:
that proves process liveness, while the new worker-run workspace heartbeat
proves bounded cognitive liveness/non-authority inside an invocation.

`infra/entrypoint.sh` needs only a comment clarifying that every supervised
`worker-run` owns one bounded workspace window and nonzero heartbeat health
causes the existing restart. `infra/docker-compose.prod.yml` should need no new
service, volume, environment variable, network path, or capability.

## Security and threat boundaries

| Boundary | Threat | Required control |
|---|---|---|
| Queue job -> workspace item | Payload/prompt/secret/provider-response leakage | Explicit allowlist adapter; fixed content; never spread `to_dict()` or payload/result/error into workspace metadata |
| Tenant runtime -> workspace service | Cross-tenant cognition or global fallback | Use `runtime_state_tenant(args)` and existing workspace tenant validation; test mismatch rejection |
| Workspace report -> public stdout | Raw selected content, trace, or internal exception leakage | Reuse canonical redaction; publish compact projection; fixed failure code only; redaction regression test |
| Shadow output -> queue/runtime | Advisory output steering retries, job order, promotion, ranking, or mutation | One-way observation after persistence; no returned value consumed by queue logic; equality test for queue outcomes with heartbeat present |
| Heartbeat failure -> supervisor | Silent failure or restart storm without evidence | Emit `ok=false` structured report before exit 1; preserve bounded supervisor backoff; no hidden restart in process |
| Metrics -> operations | High-cardinality tenant/job leakage | Fixed metric names only; no labels or identifier-derived names |
| Release evidence -> claims | Hollow, stale, or authority-changing heartbeat proof | Fail-closed schema/count/bounds/authority validation in release-audit |

The workspace remains data-not-instructions, shadow-only, non-mutating, and off
the answer critical path. This phase must not add evidence to the service,
invoke self-generated durable writes, or promote workspace advice.

## Compatibility constraints

- Preserve all existing `worker-run` keys and argument defaults; additions are
  optional schema fields for consumers but required by new release evidence.
- Preserve local, SQLite, and Postgres queue/runtime parity.
- Preserve queue cadence, order, limit, idle exit, poll interval, `--kind`, and
  `--fail-on-dead` behavior.
- Preserve job and queue results byte-for-byte apart from additive report
  fields and heartbeat metrics.
- Preserve the no-enable-toggle contract; do not add an environment/CLI enable
  flag.
- Preserve deterministic JSON serialization and existing report redaction.
- Do not mount in stdio/HTTP/streamable MCP or add an API background task.
- Do not require controller power telemetry or claim G4
  quality-per-unit-compute. This phase reports the existing bounded timing/
  estimated-compute evidence; promoted G4 quality claims still require reviewed
  operator telemetry under the existing G0 gate.

## Validation Architecture

### Test seams

Keep the normal subprocess tests for real public behavior. For failure/hard-stop
paths, use a narrow in-process seam around service construction/ticking (for
example a private service factory/helper that tests can monkeypatch) rather
than adding a user-facing enable/configuration flag. The seam must not alter the
production default and must let tests assert:

- exactly one service instance/start per `worker-run` invocation;
- one tick per productive and idle worker cycle until frozen;
- no second `start()` after hard stop;
- remaining queue cycles still complete after heartbeat failure;
- fixed redacted failure output and exit 1;
- service output never feeds queue selection or handlers.

### Red-green order

1. **RED — public lifecycle/report:** extend the existing bounded worker-run
   subprocess test to require productive and idle heartbeat ticks, compact
   per-cycle results, final summary, additive report shape, and metrics.
2. **RED — privacy/non-interference:** use a hostile job payload/result/error
   fixture and assert none appears in heartbeat output; assert queue/jobs and
   cadence are unchanged.
3. **RED — terminal hard stop/no restart:** inject a bounded controller/service
   that hard-stops, assert no later tick/start in the same invocation,
   structured final evidence, `ok=false`, and exit 1.
4. **RED — runtime exception:** inject a tick failure, prove safe queue work
   continues, the error body is absent, a fixed code is present, and exit 1
   occurs after report emission.
5. **RED — release evidence:** add focused cases rejecting missing, malformed,
   stale, unbounded, non-shadow, critical-path, mutating, and contradictory
   heartbeat proof.
6. **RED — production route:** assert the consolidator still supervises the
   same `worker-run` command and no new daemon/service/toggle exists.
7. **GREEN — minimum adapter/projection helpers:** implement only the allowlist
   adapter, compact projection, and shared validation shape needed by the red
   tests.
8. **GREEN — mount lifecycle:** wire start/tick/freeze/stop and metrics into
   `cmd_worker_run` without changing queue scheduling.
9. **GREEN — evidence enforcement:** require the additive section in release
   audit and update canonical fixtures/comments.
10. **REGRESSION:** run Phase 7 stream/heartbeat/G0 guardrails, all runtime
    backends available locally, then the full repository gates.

## No-change boundaries

- No standalone heartbeat daemon, thread, async task, process, or compose
  service.
- No MCP/API mounting.
- No workspace persistence or schema migration.
- No raw job payload/result/error/evidence/prompt/provider content.
- No effect on job choice, status, retry/dead transitions, persistence,
  promotion, prediction, replay, retrieval, ranking, or durable memory.
- No enable/disable toggle or hidden restart inside one worker invocation.
- No redesign of `ShadowWorkspaceService`, its circuit breaker, no-toggle
  contract, or Phase 7 G0 gates.
- No production rollout/operator capture and no new promoted G4
  quality-per-compute claim.

## Recommended minimal plan shape

Use one executable plan (`09.2-01-PLAN.md`) with three ordered tasks. Splitting
these into independent plans would duplicate the same `cmd_worker_run` and
release-fixture surfaces and make schema drift more likely.

1. **Contract-first tests and private adapter/projection helpers** — lock the
   additive worker schema, privacy allowlist, metrics names, and failure/hard
   stop semantics red-first.
2. **Mount the bounded service in `cmd_worker_run`** — one lifecycle per
   invocation, one tick per cycle, freeze without restart, preserve queue
   outcomes, emit final evidence, exit unhealthy when required.
3. **Enforce public/release proof and production routing** — shared release
   validation, weak-proof rejection fixtures, entrypoint/manifest assertions,
   Phase 7/G0/full verification.

The plan should remain a single wave because all three tasks touch one public
schema and should land atomically. Phase 09.3 can then consume the independent
verification artifact and requirement traceability without reopening runtime
design.
