# Phase 09.1: Preserve Caller Context Across Search, Deep Search, and Explain - Research

**Researched:** 2026-07-10
**Domain:** Public read-context propagation and fail-closed retrieval authorization
**Confidence:** HIGH

## Summary

Phase 09.1 is a narrow public-boundary repair, not an engine or access-policy redesign. The three storage engines already accept a `filt` mapping on `deep_search()` and delegate it to the same `retrieve(..., deep=True, filt=filt)` pipeline. `may_read_item()` is already the shared fail-closed authorization point. The gap is that `MemoryTools.search()` constructs most of the caller context manually, `MemoryTools.deep_search()` forwards only `role`, and `MemoryTools.explain()` forwards no context. The CLI duplicates the same asymmetry: `search` exposes the full read-context flags, `deep-search` exposes only `--role`, and `explain` exposes none.

The best implementation is therefore to reuse the two existing canonical helpers rather than add another abstraction:

1. Make `MemoryTools.search`, `deep_search`, and `explain` accept the same caller-context parameters, default `role` to `reader`, and build their filter with `MemoryTools._read_context()`.
2. Preserve `search`'s separate trust-tier retrieval controls (`min_trust_tier` / `max_trust_tier`) by adding them to the canonical context after `_read_context()` returns; they are retrieval-ranking/filter controls, not caller identity fields.
3. Make all three CLI parsers use `_add_read_context_args()` and all three dispatchers use `_read_context_kwargs()`; keep the two search-only trust-tier flags beside that helper.
4. Let signature-derived MCP schemas, JSON-RPC, and the official SDK inherit the repaired contract. Do not hand-maintain transport schemas.

This is a high-confidence, low-footprint change: two source files are sufficient, with regression coverage concentrated in the existing access-policy, CLI, MCP parity, and runtime-surface suites.

## Locked Decisions

The phase context is authoritative and constrains the plan:

- One identical caller read context across `search`, `deep_search`, and `explain`: `role`, `user_id`, `max_sensitivity`, `capability_tags`, `purpose`, `residency`, `region`, `break_glass`, and `lawful_basis`.
- Default role is `reader` when omitted on every public surface.
- The implementation must use `MemoryTools._read_context()` and the engine `filt` path. No post-retrieval filtering and no second authorization implementation.
- Optional fields remain omitted when absent; do not substitute empty strings, empty lists, or false sentinels except for the helper's required `role` and tenant identity.
- The change is additive at the call contract and must not alter the retrieval response schema.
- Denied results remain existence-silent: no inaccessible content, CID, hidden-result count, or policy-sensitive metadata may appear in `explain` output.
- Required verification spans direct `MemoryTools`, CLI, generated MCP schemas, JSON-RPC, and the official SDK.
- Phase 09.2 heartbeat mounting, Phase 09.3 milestone evidence reconciliation, and Plan A/Plan B capability work are out of scope.

## Current Architecture

### Shared runtime path

```text
CLI command / JSON-RPC tools/call / official SDK call_tool
                         |
                         v
                   MemoryTools method
                         |
                         v
         engine.retrieve or engine.deep_search(filt=...)
                         |
                         v
              shared retrieval candidate paths
                         |
                         v
                  may_read_item(...)
```

The public facade is the right repair point. Moving policy into individual transports would create drift; moving it below the engine filter would duplicate the existing enforcement path.

### Engine parity is already present

- `LocalMemoryEngine.deep_search()` (`src/mnemosyne/engine.py:2215`) delegates to `retrieve(..., deep=True, filt=filt)`.
- `SqliteEngine.deep_search()` (`src/mnemosyne/sqlite_engine.py:2646`) does the same.
- `PostgresEngine.deep_search()` (`src/mnemosyne/postgres_engine.py:4004`) does the same.
- `MemoryTools.explain()` intentionally uses `engine.deep_search()` and returns its existing `RetrievalResult.to_dict()` shape. It should continue doing so, now with the same filter.

No engine signature or response type needs to change.

### Canonical access-policy semantics

`may_read_item()` (`src/mnemosyne/access_policy.py:235`) is existence-silent at the caller layer and currently enforces:

- known role and the role-specific sensitivity ceiling;
- tenant and policy-tenant equality;
- restricted/hold, expiry, erased, inactive, and S4-raw denial;
- two-sided operator break-glass for S2/S3 (`context.break_glass`, policy `break_glass`, and operator role);
- item-level maximum sensitivity;
- allowed roles and required capability subset;
- allowed principals from `user_id` / subject / principal / source identity;
- scope and purpose intersection;
- residency or region compatibility;
- lawful-basis intersection;
- raw-field redaction or denial based on minimum role.

The phase must test propagation into this existing function; it must not change these decisions.

## Exact Public Contract

### Canonical caller-context parameters

All three `MemoryTools` methods should expose these parameters with the same types, order, and defaults already established by `_read_context()`:

| Parameter | Type | Default / omission behavior |
|---|---|---|
| `role` | `WriteRole` | `"reader"`; always included in context |
| `user_id` | `str | None` | omitted when absent/empty |
| `max_sensitivity` | `int | None` | omitted only when `None`; zero remains meaningful |
| `capability_tags` | `list[str] | None` | copied and omitted when absent/empty |
| `purpose` | `str | list[str] | None` | omitted only when `None` |
| `residency` | `str | None` | omitted when absent/empty |
| `region` | `str | None` | omitted when absent/empty |
| `break_glass` | `bool` | `False`; included only when true |
| `lawful_basis` | `str | list[str] | None` | omitted only when `None` |

`_read_context()` also includes both `tenant_id` and `tenant` with the same caller tenant. This is desirable defense in depth because `may_read_item()` recognizes both keys and checks them against the item tenant.

### Search-only controls

`min_trust_tier` and `max_trust_tier` should remain on `search` only unless a later phase explicitly expands retrieval controls. They are not among the locked caller-context fields. Preserve the current precedence: `max_trust_tier` wins when both are supplied; otherwise use `min_trust_tier`.

### Default-role compatibility

The CLI already defaults `search` and `deep-search` to `reader`, and `_add_read_context_args()` defaults every read command to `reader`. The inconsistent Python facade defaults are `agent` for `search` and `deep_search`, while `explain` relies on the engine's implicit reader behavior. Normalizing all three facade signatures to `reader` is a security-narrowing compatibility change required by the locked context. Generated MCP schemas will advertise the new `reader` default automatically. Existing callers that need agent-level S2 access must already provide a valid role/context explicitly after this phase.

## Source Changes to Plan

### `src/mnemosyne/mcp_tools.py`

- Refactor `MemoryTools.search()` to call `_read_context()` rather than rebuilding the same mapping manually.
- Retain search-only trust-tier insertion after the helper call.
- Expand `MemoryTools.deep_search()` and `MemoryTools.explain()` with the identical optional caller-context signature.
- Pass the canonical mapping as `filt` to `engine.deep_search()` in both methods.
- Keep timing/metrics calls and `to_dict()` behavior unchanged.

Ponytail constraint: do not add a new context class, dataclass, policy adapter, or generalized retrieval wrapper. `_read_context()` is already the rung that holds.

### `src/mnemosyne/cli.py`

- Change `cmd_search()` to pass the two trust controls explicitly and expand `**_read_context_kwargs(args)` for the caller context.
- Change `cmd_deep_search()` and `cmd_explain()` to expand the same helper.
- Use `_add_read_context_args(search)`, `_add_read_context_args(deep)`, and `_add_read_context_args(explain)` in `build_parser()`.
- Keep `--min-trust-tier` and `--max-trust-tier` explicitly on `search` before or after the shared helper.

This removes parser/dispatch duplication and ensures future read-context fields have one CLI definition.

### No planned source changes elsewhere

- Do not modify `access_policy.py`; its semantics are already correct.
- Do not modify Local/SQLite/Postgres engine implementations; all already forward `filt`.
- Do not edit `TOOL_SPEC`, JSON schema tables, JSON-RPC handlers, or official SDK handlers. `_to_mcp_tool_spec()` derives `properties`, `required`, types, nullable unions, and defaults from `MemoryTools` signatures.
- Do not change response models or add a dependency.

## Transport and Schema Behavior

### Generated MCP and CLI tools schemas

`_to_mcp_tool_spec()` (`src/mnemosyne/mcp_server.py:538`) inspects the concrete `MemoryTools` signature. Optional parameters become non-required properties with their defaults; unions are represented with `anyOf`, including explicit null. `MnemosyneMcpServer.tool_specs`, JSON-RPC `tools/list`, and CLI `mneme tools` therefore share one schema source.

Existing guards to reuse:

- `tests/test_parity_mcp.py::test_generated_input_schema_required_matches_method_signature`
- `tests/test_parity_mcp.py::test_tools_list_advertises_every_blueprint_operation_with_valid_schema`
- `tests/test_cli_runtime_tools.py::test_cli_tools_matches_mcp_tools_list_contract`

Add a focused assertion for `search`, `deep_search`, and `explain` that the nine caller-context properties are present, optional, correctly typed, and default `role` to `reader`. This makes the phase intent explicit even though the generic parity tests also protect it.

### JSON-RPC

`MnemosyneMcpServer.handle()` prepares arguments, validates them against the generated schema, then dispatches through `call_tool()`. No special JSON-RPC mapping is needed. A JSON-RPC regression should call a policy-protected record through both `deep_search` and `explain`, proving an allowed context returns it and a mismatched/missing context does not.

### Signed-session binding

`prepare_tool_arguments()` strips transport metadata, verifies a signed session, and `_bind_session_identity()` binds `tenant_id`, `user_id`, and `role` whenever those names exist in the method signature. Adding `user_id` and `role` to both methods therefore improves session parity without transport code changes:

- explicit tenant/user mismatches still fail closed;
- session role overrides an untrusted argument role;
- purpose, capability, sensitivity, residency, region, lawful basis, and break-glass remain explicit tool arguments because they are not session identity claims.

### Official SDK

`build_sdk_server()` uses the same tool specs, calls the same `prepare_tool_arguments()`, validates with the same schema, and dispatches through the same facade. Extend the existing in-process SDK request-handler pattern in `test_official_mcp_sdk_adapter_binds_signed_session_like_json_rpc`; do not stand up a new network server for this phase.

## Test Strategy

### 1. Exact filter construction

Add a focused direct-facade test using the repository's existing lightweight engine/test-double conventions (or a minimal recording engine if no suitable one exists) to assert:

- all three methods pass identical context keys for identical inputs;
- both tenant aliases and role are present;
- absent optional values are not present;
- `max_sensitivity=0` is preserved;
- `break_glass=False` is omitted and `True` is preserved;
- `search` retains trust-tier precedence without those keys appearing in deep/explain.

This catches plumbing drift more precisely than inference from result ranking alone.

### 2. Direct policy behavior

In `tests/test_access_policy_enforcement.py`, seed distinct uniquely searchable records and parameterize the public facade operation over `search`, `deep_search`, and `explain`. Cover at least these cases:

| Control | Allowed case | Filtered/denied case |
|---|---|---|
| Principal | matching `user_id` | absent or different user |
| Role + capability + purpose | allowed role, required tag, matching purpose | each missing/wrong independently |
| Sensitivity | compatible role/ceiling | `max_sensitivity` below item sensitivity |
| Residency/region | matching residency or region | incompatible location |
| Lawful basis | intersecting basis | missing/wrong basis |
| Break glass | operator + item opt-in + request opt-in | missing request opt-in or non-operator |

Do not multiply every combination across every transport. Establish full semantic coverage once at the direct facade, then use representative compound contexts at higher layers.

### 3. CLI parsing and end-to-end dispatch

In `tests/test_cli_runtime_tools.py`:

- Add parser assertions or end-to-end subprocess calls proving both `deep-search` and `explain` accept every shared flag.
- Use the existing `run_cli(store, ...)` helper against a seeded durable local store.
- Exercise one compound allowed context and one denied context for each command.
- Confirm omitted context behaves as reader.
- Keep the existing gist-abstention test intact; it protects response behavior unrelated to authorization.

The first red run should fail at argument parsing for most deep/explain flags and/or return a result that should have been filtered.

### 4. Schema and JSON-RPC parity

In `tests/test_parity_mcp.py` and/or `tests/test_runtime_surfaces.py`:

- Assert the exact shared property set and `role.default == "reader"` for all three generated input schemas.
- Retain generic signature/required/property parity and CLI-vs-MCP equality.
- Through `MnemosyneMcpServer.handle()`, exercise `deep_search` and `explain` with an allowed and denied context.
- Assert a denied serialized result contains neither the protected content nor its CID and exposes no positive hidden-result indicator.

### 5. Official SDK parity

- Use `pytest.importorskip("mcp")`, `build_sdk_server()`, and the in-process `types.CallToolRequest` handler.
- Use a signed session so tenant/user/role binding is covered, plus explicit non-identity policy fields.
- Exercise at least one of `deep_search` / `explain` as allowed and the other as denied, or both if the test remains compact.
- Assert `isError` remains false for an authorized request that simply has zero visible hits; policy filtering is not a transport error.

## Metadata-Leakage Assertions

For denied/filtering tests, check the complete serialized response rather than only `hits == []`:

- protected raw content absent;
- protected CID absent;
- no relation hit or provenance entry references the protected item;
- no gist-support ID or workspace advisory references it;
- no hidden result count or denial reason reveals item existence;
- public response keys remain identical to the established retrieval result schema.

Avoid asserting internal `AccessDecision.reason` through the public API. That reason is for local testing/diagnostics and must not become a new response field.

## Common Pitfalls

### Duplicating the context mapping

Adding fields independently to three methods would recreate the drift that caused this audit gap. Use `_read_context()` in all three methods and `_read_context_kwargs()` / `_add_read_context_args()` in all three CLI commands.

### Treating empty values as explicit authority

An empty list/string is not equivalent to an absent optional field for every policy operation. Preserve `_read_context()` omission rules exactly. In particular, preserve numeric zero for sensitivity and only include break-glass when true.

### Calling `engine.explain()`

The engine-level `explain()` signatures do not uniformly accept `filt`. The public `MemoryTools.explain()` already routes through `engine.deep_search()` to obtain a `RetrievalResult` and metrics. Continue that established path rather than expanding every engine's separate convenience method.

### Breaking trust-tier behavior while deduplicating search

`_read_context()` deliberately does not own `min_trust_tier` or `max_trust_tier`. Reinsert those search-only controls with the current max-over-min precedence.

### Hand-editing generated schemas

The schemas are signature-derived. Editing `TOOL_SPEC` or transport schema dictionaries would add a second source of truth and undermine the generic parity tests.

### Mistaking a filtered result for a transport error

Valid context that cannot authorize a record should return the normal retrieval response with no visible hit, not JSON-RPC/SDK `isError=true`. Invalid schema or invalid signed-session identity remains a transport/tool error.

### Over-expanding into runtime residency policy

The locked surface includes `residency` and `region`, matching `_read_context()`. `runtime_residency` is an internal/provider deployment concept and is not part of the Phase 09.1 public contract.

### Red-green execution order

1. **Red: public facade and CLI.** Add direct behavior/filter tests and CLI flag tests first. Confirm failures demonstrate missing propagation or parser rejection, not a bad fixture.
2. **Green: shared helper reuse.** Change only `mcp_tools.py` and `cli.py`; rerun the focused direct/CLI tests.
3. **Red/green: schemas and transports.** Add exact generated-schema, JSON-RPC, and SDK assertions; they should either fail before the signature change or pass immediately from the shared fix. Any transport-specific source edit is a warning sign and should be justified before proceeding.
4. **Regression and hygiene.** Run focused suites, then full local tests/lint, then GSD/CBM/gbrain/GitHub checks.

### Nyquist sampling rule

Every implementation task leaves a runnable automated check at the closest layer:

- helper/signature task -> direct facade filter test;
- CLI task -> subprocess parser/dispatch regression;
- transport/schema task -> generated schema + JSON-RPC/SDK regression;
- phase completion -> full pytest, Ruff, GSD consistency, CBM/gbrain freshness, and green GitHub CI.

No task should rely only on the full suite as its first observable feedback.

## Recommended Plan Shape

One plan with three implementation tasks is sufficient and keeps the change atomic:

1. **Lock the failing contract with red tests.** Add exact direct-context, policy behavior, CLI flag, schema, JSON-RPC, SDK, and leakage assertions. Run the selected nodes and record the expected failures.
2. **Repair the shared public flow.** Reuse `_read_context()` in all three facade methods; reuse the two CLI helpers; preserve search trust-tier behavior; run focused tests and Ruff.
3. **Prove parity and close the phase.** Run the complete focused set, full local gate, GSD consistency, diff hygiene, CBM impact/refresh, gbrain sync/doctor, push, and verify CI. Produce the phase summary/verification artifacts required by the active GSD workflow.

Splitting source implementation into separate facade and CLI commits is unnecessary unless the test-first workflow naturally produces two substantial, independently green increments. The facade and CLI changes form one contract repair and should not be shipped in a half-parity state.

## Open Questions

No user decision is required. The locked context resolves the only material ambiguity: default role must normalize to `reader`, even though two direct Python method defaults are currently `agent`.

One implementation-time check remains: choose the smallest existing test-double pattern for recording the exact engine filter. If no appropriate reusable stub exists, a tiny test-local recorder is preferable to adding production abstraction.
