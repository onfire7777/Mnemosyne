# Phase 09.1: Preserve Caller Context Across Search, Deep Search, and Explain - Context

**Gathered:** 2026-07-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the v1.0 milestone-audit gap by making `search`, `deep_search`, and `explain` preserve and enforce one semantically identical caller read context across MemoryTools, CLI, generated MCP schemas, JSON-RPC, and SDK transports. Semantic parity means the same field set, types, defaults, canonical `_read_context()` output, and generated-schema meaning; it does not require identical Python parameter order. The phase covers REQ-003, REQ-004, REQ-007, and NFR-004 only; it does not redesign access policy or change response schemas.

</domain>

<decisions>
## Implementation Decisions

### Contract compatibility
- Reuse `search`'s existing optional caller-context parameters: role, user identity, sensitivity ceiling, capability tags, purpose, residency, region, break-glass state, and lawful basis.
- Preserve the established positional contract: do not reorder `search` (including its existing `max_sensitivity` before `role`), and keep `deep_search`'s existing fourth-position `role`. Append newly exposed optional fields after each method's existing parameters; do not make existing parameters keyword-only.
- Require semantic and generated-schema parity across the three methods, not identical signature order. Exercise newly exposed context fields by keyword so compatibility tests do not create a new positional convention.
- Normalize omitted context to the locked `reader` behavior; supplied context remains fail-closed when it cannot authorize the read.
- Mirror the established read-context CLI flags on both `deep-search` and `explain`.
- Keep the change additive: optional parameters only, no response-schema break, no new core dependency, and no bypass of the public MemoryTools boundary.

### Enforcement semantics
- Build the existing `MemoryTools._read_context()` representation and pass it into the shared engine retrieval filter; do not add post-retrieval filtering or a parallel policy path.
- Normalize `search`, `deep_search`, and `explain` to the established `reader` default unless an explicit caller role is supplied. This is an intentional security-narrowing default change, separate from and not permission to reorder parameters.
- Omit absent optional fields exactly as `_read_context()` already does; do not populate ambiguous empty sentinel values.
- Denied or filtered explanations expose no hidden-result counts, CIDs, existence signals, or policy-sensitive metadata.

### Verification and compatibility
- Add red-first regression coverage proving the current context-loss behavior across MemoryTools and CLI before implementing the fix, plus compatibility regressions proving legacy positional `search` and `deep_search` calls retain their established argument meaning.
- Cover purpose, user, capability, sensitivity, residency/region, lawful basis, and break-glass propagation, including allowed, filtered, and denied cases.
- Verify generated MCP input schemas and CLI `tools` schemas remain in parity for all three read methods, then exercise JSON-RPC and official SDK call paths.
- Run focused access-policy/runtime/CLI suites, full pytest, Ruff, GSD consistency, diff hygiene, CBM impact/refresh, gbrain sync/doctor, and GitHub CI before phase completion.

### the agent's Discretion
- Choose the smallest shared helper reuse and exact test placement that matches existing repository conventions.
- Preserve naming and ordering conventions already established by `_read_context_kwargs`, `_add_read_context_args`, and `MemoryTools._read_context`.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `MemoryTools.search` already accepts the complete caller read context.
- `MemoryTools._read_context` already constructs the canonical engine filter without empty optional fields.
- CLI helpers `_read_context_kwargs` and `_add_read_context_args` already centralize parsing and dispatch of the full context surface.
- `may_read_item` is the existing fail-closed access-policy enforcement point.

### Established Patterns
- Public CLI and MCP calls route through `MemoryTools`; engines remain behind that mediated facade.
- Read denials are fail-closed and must not reveal inaccessible data or existence metadata.
- CLI and generated MCP schemas are tested for parity rather than maintained as separate contracts.
- Root-cause fixes belong in the shared flow and leave one runnable regression gate.

### Integration Points
- `src/mnemosyne/mcp_tools.py`: `MemoryTools.deep_search`, `MemoryTools.explain`, and `_read_context` reuse.
- `src/mnemosyne/cli.py`: command dispatch plus `_read_context_kwargs` and `_add_read_context_args` reuse.
- `src/mnemosyne/access_policy.py`: existing `may_read_item` enforcement semantics.
- `tests/test_access_policy_enforcement.py`, `tests/test_cli_runtime_tools.py`, and `tests/test_runtime_surfaces.py`: focused regression and transport coverage.

</code_context>
