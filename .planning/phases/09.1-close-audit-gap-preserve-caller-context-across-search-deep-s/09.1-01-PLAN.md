# Phase 09.1 Plan 01: Preserve Caller Read Context End to End

<objective>
Close the v1.0 milestone-audit authorization gap by preserving one canonical,
fail-closed caller read-context meaning across `search`, `deep_search`, and `explain`
through MemoryTools, CLI, signature-derived MCP schemas, JSON-RPC, and the
official SDK. Keep response schemas and existing access-policy semantics
unchanged, preserve search trust-tier precedence, and prove that denied reads
remain existence-silent.
</objective>

<execution_context>
Execute as one atomic TDD plan in Wave 1. Follow the Ponytail minimum-code
ladder: reuse `MemoryTools._read_context`, `_read_context_kwargs`, and
`_add_read_context_args`; add no dependency, context model, transport schema,
engine filter, or access-policy implementation. Use systematic debugging: make
the public-contract tests fail for the known context-loss cause, repair that
shared cause in the two public-boundary files, then rerun focused and full
gates. Use CBM impact analysis before production edits and refresh CBM plus
gbrain after the final source state is committed.
</execution_context>

<threat_model id="T-09.1-01" block_on="high">
  <boundary>Caller-controlled authorization context crosses CLI, JSON-RPC, and official SDK inputs into signature-derived MemoryTools calls and the shared retrieval authorization filter.</boundary>
  <assets>Tenant-isolated evidence, protected assertions, provenance/CIDs, caller identity, sensitivity controls, capability and purpose grants, residency and lawful-basis constraints.</assets>
  <risks>
    <risk severity="high">Context loss or omission widens `deep_search` or `explain` beyond the authorization enforced by `search`.</risk>
    <risk severity="high">Caller-supplied tenant, user, or role conflicts with signed-session identity and permits cross-identity reads.</risk>
    <risk severity="high">Post-filtering or divergent transport schemas create a privilege-widening bypass of `may_read_item`.</risk>
    <risk severity="high">Denied explanations disclose protected content, CIDs, hidden-result counts, provenance, or policy-sensitive denial metadata.</risk>
  </risks>
  <controls>
    <control>Build all three filters with `MemoryTools._read_context()` and send them through the existing engine `filt` path to `may_read_item()`.</control>
    <control>Preserve `search`'s established positional order, including `max_sensitivity` before `role`, and preserve `deep_search`'s fourth-position `role`; append new optional fields without making existing parameters keyword-only.</control>
    <control>Default omitted roles to `reader`; omit absent optional values exactly as the canonical helper does; preserve meaningful zero and explicit true values.</control>
    <control>Let MemoryTools signatures generate MCP, JSON-RPC, CLI-tools, and SDK contracts; do not duplicate transport schemas.</control>
    <control>Retain signed-session tenant/user mismatch rejection and server-bound role behavior, and test representative identity conflicts through JSON-RPC and SDK.</control>
    <control>Assert the complete denied response is existence-silent across direct, CLI, JSON-RPC, and SDK surfaces.</control>
  </controls>
  <verification>Block execution or completion on any high-severity finding, any protected identifier/content leak, any identity-binding regression, or any public surface that lacks the canonical nine optional context fields.</verification>
</threat_model>
