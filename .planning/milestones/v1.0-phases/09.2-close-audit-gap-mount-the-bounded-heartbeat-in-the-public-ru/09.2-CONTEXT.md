# Phase 09.2: Mount the Bounded Heartbeat in the Public Runtime - Context

**Gathered:** 2026-07-10
**Status:** Ready for planning
**Mode:** Autonomous recommendations accepted by the user

<domain>
## Phase Boundary

Mount the existing `ShadowWorkspaceService` into a supported public runtime so the bounded always-on heartbeat actually runs during normal worker operation and is observable in public/runtime evidence. This phase does not redesign the workspace, promote it to answer or mutation authority, add a new daemon, or reopen Phase 7's safety rails.

</domain>

<decisions>
## Implementation Decisions

### Runtime host
- **D-01:** The canonical host is the existing `mneme worker-run` lifecycle. The production `mnemo-consolidator` already supervises that command through `infra/entrypoint.sh`, so mounting there covers local/SQLite/Postgres CLI operation and the deployed worker without introducing another service.
- **D-02:** Do not mount the continuous loop in request-scoped MCP/API processes. Stateless MCP rebuilds tools per request and is the wrong lifecycle owner; the API remains a read/request surface, not a background cognitive supervisor.
- **D-03:** Do not add a new executable, daemon, container, dependency, or side channel unless research proves `worker-run` cannot meet a locked requirement.

### Cadence and bounded lifecycle
- **D-04:** Start one `ShadowWorkspaceService` window per bounded `worker-run` invocation and tick it exactly once for every worker cycle, including productive and idle cycles.
- **D-05:** Reuse the existing controller limits, anti-rumination regulator, max-cycle circuit breaker, and explicit `start()`/`stop()` lifecycle. There is no enable flag and no unbounded loop.
- **D-06:** A terminal heartbeat hard stop freezes the workspace for the remainder of that worker invocation. Do not silently call `start()` again inside the same invocation or reset safety counters. The production supervisor may start a fresh bounded process window after the unhealthy invocation exits.
- **D-07:** Preserve the worker's existing queue cadence, idle-exit, polling, and fail-on-dead behavior. Heartbeat work is bounded within each existing cycle and must not create a second scheduler.

### Privacy-safe tick inputs and authority
- **D-08:** Build workspace items only from bounded tenant-scoped job metadata such as job id, kind, status, cycle number, and outcome class. Never pass raw queue payloads, evidence content, prompts, secrets, error bodies, or provider responses into the heartbeat.
- **D-09:** Treat all heartbeat output as shadow-only, advisory-only, data-not-instructions, off the answer critical path, and non-mutating. It must not change job selection, retry/dead state, promotion, prediction gates, replay priority, retrieval ranking, or durable memory writes.
- **D-10:** Tenant identity comes from the existing runtime/queue tenant resolution. Cross-tenant items are rejected by the existing workspace policy path; no fallback to a global/system tenant is allowed when an explicit runtime tenant exists.

### Public observability and evidence
- **D-11:** Add a redacted heartbeat result to every worker cycle and a top-level final heartbeat summary containing the existing `always-on-heartbeat-safety.v1` fields, lifecycle state, tick count, stopped reason, shadow/critical-path/mutation flags, and bounded timing/cost signals already available from the service.
- **D-12:** Export low-cardinality metrics for tick, idle/productive tick, hard-stop, unhealthy, and bounded duration/compute evidence using the existing runtime metrics surface. Do not log raw workspace items or create unbounded tenant/job label cardinality.
- **D-13:** Extend worker-run/release evidence validation so an invocation cannot claim the heartbeat is mounted when the report is missing, malformed, stale within the invocation, non-shadow, critical-path, mutating, or not bounded. Preserve the existing worker report schema additively.
- **D-14:** Update the production entrypoint/runbook comments and tests only as needed to make the existing consolidator supervision contract explicit. No live production rollout or operator capture is required to prove the source/runtime mounting phase, but the path must be runnable by the existing production command.

### Failure semantics
- **D-15:** Heartbeat failures are never silent. Continue already-safe durable queue processing so the shadow path cannot corrupt or strand jobs, but mark the worker report `ok: false`, emit a redacted structured heartbeat failure, and exit nonzero after the bounded reporting path so the existing supervisor restarts the worker.
- **D-16:** A normal terminal safety hard stop is a visible unhealthy heartbeat outcome, not an exception that erases the report. Preserve the final safety evidence and never tick again in the stopped window.
- **D-17:** Worker output remains deterministic and JSON-serializable. No raw exception text, secret-bearing payload, or internal content may be emitted through the public heartbeat fields.

### Verification expectations
- **D-18:** Use red-first tests covering productive cycles, idle cycles, terminal hard stop, failure reporting, no silent restart, bounded inputs, non-interference with queue outcomes, additive report shape, local CLI persistence, production entrypoint routing, and release-evidence rejection of weak heartbeat proof.
- **D-19:** Prove all existing Phase 7 heartbeat/stream/G0 guardrails remain green and run the full suite, Ruff, GSD consistency, CBM/gbrain synchronization, exact-SHA CI, clean review, security audit, and independent phase verification before completion.

### the agent's Discretion
- Exact helper names and the smallest internal adapter between a worker cycle and `WorkspaceItem` metadata.
- Whether the final heartbeat summary is stored as a dedicated top-level `heartbeat` object or a clearly versioned `workspace_heartbeat` object, provided existing worker report keys remain compatible and evidence validators share one source of truth.
- The precise low-cardinality metric names, following existing naming conventions and avoiding new dependencies.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ShadowWorkspaceService`: already provides explicit `start()`/`stop()`, stateful `tick()`, idle item generation, bounded cycles, proto-self/metacognition, terminal hard stops, redacted reports, and shadow/non-mutation flags.
- `cmd_worker_run`: already owns bounded productive/idle cycles, queue persistence, metrics, final JSON output, and nonzero failure behavior.
- `_runtime_worker_components` and `runtime_state_tenant`: existing backend-neutral runtime/tenant construction shared by local, SQLite, and Postgres worker execution.
- `infra/entrypoint.sh` consolidator role: already supervises repeated bounded worker invocations, so it supplies the long-running production lifecycle without a new daemon.
- Existing worker release-evidence validators and runtime metrics: established public proof surfaces that can absorb additive heartbeat evidence.

### Established Patterns
- Background cognition is shadow-only and advisory; durable writes remain owned by the consolidation/queue path and existing authorization rails.
- Runtime reports are structured JSON with redacted, bounded evidence; release audit rejects missing or weak required sections.
- Public runtime behavior is backend-neutral above the queue/engine adapters and is tested through CLI subprocess execution plus production manifest/entrypoint assertions.
- Safety failures are explicit and machine-checkable; they are never hidden behind successful unrelated work.

### Integration Points
- Construct the service beside worker components in `cmd_worker_run` or one focused helper, start it before the first cycle, tick after each cycle has a bounded job-metadata view, and stop/preserve its report in `finally`-safe flow.
- Add heartbeat evidence to the existing cycle/final report and metrics before `emit(report)`.
- Extend worker-run evidence validation and production command tests so source/runtime mounting is enforced rather than documentation-only.

</code_context>

<specifics>
## Specific Ideas

- “Always-on” means active during the real supervised worker lifecycle, not a new unbounded thread and not merely a unit-test fixture.
- A hard stop must remain meaningful: the worker may continue safe queue bookkeeping, but the cognitive window stays frozen and the process exits unhealthy so supervision can create a fresh bounded window.
- Public evidence should prove both liveness and non-authority: it ran, it was bounded, it stayed shadow-only, and it did not mutate or steer the worker.

</specifics>

<deferred>
## Deferred Ideas

- Mounting the heartbeat in request-scoped MCP/API processes.
- Adding a standalone heartbeat daemon or container.
- Promoting workspace output into answer authority, retrieval ranking, prediction gates, replay priority, or mutation without the already-required explicit gates.
- Live production rollout/capture; this phase makes the existing production path source-runnable and evidence-capable, while operator capture remains a separate evidence action when required.

</deferred>
